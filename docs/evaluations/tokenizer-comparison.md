# HanLP 与 trigram 实测对照（2026-09-14）

这次结果不支持“HanLP 全面优于 trigram”。真实关键词查询的命中相同；部分函数名、文件名搜索由 trigram 胜出。HanLP 的词边界能减少某些无关子串匹配，索引也较小，但建索引和首次模型加载更贵。

## 比较方法

比较的是**普通关键词搜索**，不是 RAG 答案正确率，也不是独立中文分词 F1。两边使用完全相同的会话正文、字段、会话级索引粒度和原项目的字段/摘要评分函数。查询词之间采用 AND；时间分数统一、同分按 ref 稳定排序。没有 embedding，也没有调用回答模型。

三组配置：

1. **HanLP**：当前模型、技术词典、代码规则生成索引词和查询词，词编码后写入 FTS5。
2. **trigram 原方案**：FTS5 trigram，查询按空白切分；不足三个字符的查询词使用转义后的 SQL LIKE，保留原短词处理方式。评分使用原函数，未直接拿不同分词方式的 BM25 数值比较。
3. **trigram 同查询词对照**：索引仍是 trigram，但查询词完全复用 HanLP 生成的词。这组隔离“查询是否做了中文分词”和“索引按词还是子串匹配”的影响；它本身依赖 HanLP，不能视为纯 trigram 的成本。

所有配置对每条查询显式预热，再交替顺序执行五次，并检查每次排序一致。绕过 JavaScript 查询缓存，但 Python 分词片段缓存保留；另测第一次处理新查询的时间。冷模型加载单独计时。分词器版本、语料/问题/脚本 SHA-256、SQLite/Electron 版本见 [机器可读结果](tokenizer-comparison.json)。

## 命中与排序

Hit@5 表示前五条结果中至少有一个已标注的正确会话，分母只含有答案问题。Recall@5 则统计找全已标注相关会话的比例，多答案时两者不同。

| 测试集 | 有答案问题数 | HanLP Hit@5 | trigram 原方案 Hit@5 | trigram 同查询词 Hit@5 |
| --- | ---: | ---: | ---: | ---: |
| 既有合成历史，自然语言/技术词混合问题 | 40 | 21/40（52.5%） | 18/40（45%） | 21/40（52.5%） |
| 专门构造的词边界、代码片段等 | 18 | 14/18（77.8%） | 18/18（100%） | 18/18（100%） |
| 冻结真实历史，完整自然语言问题 | 23 | 2/23（8.7%） | 0/23（0%） | 2/23（8.7%） |
| 从真实问题人工缩短的关键词输入 | 17 | 14/17（82.4%） | 14/17（82.4%） | 14/17（82.4%） |

这几组中，找到目标时目标均排第一，因此 MRR@5 与 Hit@5 数值相同。词边界组的宏平均 Recall@5 为 HanLP 75%、trigram 100%，因为 HanLP 还有一题只找到两个相关文档中的一个。其余组 Recall@5 与 Hit@5 相同。各组 Precision@5（分母固定为五）在 JSON 中保留；候选语料很小、相关标注未穷尽，不能把它当作真实用户的精度。

三组分别包含 10、2、7 个无答案问题，两种方案和同查询词对照均没有返回候选。人工关键词改写组没有新增无答案问题。这个小样本结果不代表全量历史中没有误召回。

自然语言问题结果低，主要因为普通搜索要求**每个查询词都命中**，原方案更要求连续子串。它们是对输入形式的压力测试，不代表 RAG 的召回率。之前 HanLP 97.5% 的成绩来自 **RAG 的 OR + BM25 片段召回**，不是这里的 AND 会话搜索，两项成绩不可直接比较。

## 具体差异

- `getUser`、`UserSess`、`rag_serv`、`CONNECTION_REF`：相关完整标识符确实存在。trigram 四题均找到，HanLP 四题均未找到。现有代码拆分规则保留完整词和组成词，不能覆盖任意半截字符串。
- `内存`：trigram 同时找到“内存泄漏”和“内存池”；HanLP 只找到前者，显示新复合词仍可能导致漏召回。
- `数据`：这一人工用例特意将需求定义为独立“数据”词。HanLP 只返回“数据清洗”；trigram 还返回两个包含“数据库”的文档。若用户本就想找“数据库”，相关性判断应改变，所以这不是普遍优劣结论。
- 双方使用相同查询词后，自然语言和真实关键词两组的命中相同。这说明目前观察到的部分收益来自**查询预处理**，并不能证明“必须替换 trigram 索引”。

## 耗时与存储

以下使用第一次建立的真实历史索引：7 个会话、约 80.7 KB UTF-8 文本。这个规模只能测本地小样本开销，不能外推万条会话的吞吐。

| 项目 | HanLP | trigram 原方案 |
| --- | ---: | ---: |
| 模型已加载后的索引建立 | 6.93 秒 | 0.033 秒 |
| SQLite 文件（包含相同原文表） | 248 KiB | 656 KiB |
| 新增 FTS 索引空间 | 156 KiB | 564 KiB |
| 17 条关键词输入的重复热查询 P95 | 0.81 ms | 0.40 ms |

本轮 HanLP 模型冷加载约 10.1 秒；模型已加载后，真实自然语言问题首次分词的 P95 约 19.8 ms。不要把上表的重复缓存查询当成第一次输入问题的延迟。这些时间不含 HTTP、UI 渲染和磁盘会话解析，且是当前机器和后台负载下的结果。

人工关键词组再次建索引时复用了同一批原文的 HanLP 分词缓存，因此只耗时约 42 ms；不能拿这次重复构建成绩代替前面的 6.93 秒。所有构建结果均保留在 JSON 中。

## 范围与可复现性

- 共 117 条查询输入，其中人工缩短的 17 条源自既有真实问题，不能当作 117 个独立样本。
- 合成历史 10 个会话；真实历史仅 7 个会话、4 个项目；另有 12 条人工边界文档。
- 真实问题及原 gold 是既有冻结集的 Agent 标注，并非自然搜索日志抽样或独立人工复核。新增关键词改写与边界题也是 Agent 编制；本次没有据结果调整分词器、词典或生产搜索配置。
- 真实原文、查询、逐条候选及临时数据库保留在忽略目录 `.agent-snapshots/tokenizer-comparison/2026-09-14T13-57-57-067Z/`。公开 JSON 只包含汇总和按题目 ID 的差异，不包含真实会话正文。

```powershell
corepack pnpm setup:hanlp
corepack pnpm eval:tokenizers
```

需要开发依赖里的 Electron，以确保使用真实 FTS5/trigram。真实数据读取 `.agent-snapshots/rag-eval/dataset-v2.json`，关键词改写读取同目录 `keyword-queries.json`；其他机器没有这些私有文件时只能复现公开合成部分。每轮详细结果写入新的时间戳目录，公开摘要更新到本目录 JSON。

结论：当前 HanLP 配置适合按完整词和技术概念搜索，trigram 更适合局部字符串查找。这次评测支持按搜索需求选择和补充检索能力，不支持“复杂模型必然更准确”。
